로봇이 GitHub과 대화하는 법

요즘은 사람뿐 아니라 자동화 프로그램, AI 에이전트도 GitHub을 다뤄요. 그들은 화면을 클릭하지 않아요. 그럼 어떻게 대화할까요? gh CLI, 폴링과 이벤트, 그리고 자주 오해받는 'GitOps'라는 이름까지 정리해 볼게요.

이렇게도 써요

운영팀이 매일 반복하는 일(이슈 확인, 보고서 갱신, 배포)을 자동화 프로그램이나 AI 에이전트에게 맡기는 곳이 늘어요. 그 로봇들이 GitHub과 '대화'하는 방식이 이 페이지의 주제예요.

자동화 운영 사례 보기 →

집배원과 초인종

새 편지가 왔는지 확인하는 방법은 두 가지예요. 하나는 집배원처럼, 정해진 시간마다 우편함을 열어 "새 편지 있나?" 하고 직접 확인하는 방식. 다른 하나는 초인종처럼, 편지가 오면 '딩동' 소리가 울려 그때 나가는 방식.

자동화 프로그램이 GitHub 변화를 감지하는 방식도 딱 이 둘이에요. 앞의 것을 폴링(polling), 뒤의 것을 이벤트 기반(event-driven)이라 불러요. 이 페이지 뒤쪽에서 둘을 자세히 비교할 거예요. 우선은 "확인하러 가기 vs 알림 받기"라는 그림만 기억해 두세요.

비유

gh CLI는 로봇을 위한 '표준 창구'예요. 사람은 은행 앱 화면을 손가락으로 누르지만, 로봇은 창구에 대고 정해진 문장("이슈 목록 주세요")으로 요청해요. 매번 새로 길을 찾을 필요 없이, 늘 같은 창구에 같은 말투로 말하면 되니 실수가 적어요.

gh CLI: 로봇의 손과 입

사람은 GitHub을 웹브라우저에서 클릭으로 다뤄요. 하지만 자동화 프로그램이나 AI 에이전트는 화면을 볼 수 없어요. 대신 gh CLI라는 명령어 도구로 GitHub과 대화해요. T18에서 살짝 만났던 그 gh예요. 터미널에 문장처럼 명령을 적으면, GitHub이 그대로 응답해요.

gh issue list                   # 지금 열려 있는 이슈 목록을 보여줘
gh issue view 42                # 42번 이슈의 내용을 보여줘
gh pr create                    # 지금 브랜치로 새 PR(제안)을 만들어줘
gh pr view 17                   # 17번 PR의 상태와 리뷰를 보여줘
gh pr merge 17                  # 17번 PR을 승인·병합해줘

그런데 궁금하지 않나요? GitHub에는 프로그램용 정식 통로인 REST/GraphQL API도 있어요. 그런데 왜 로봇들은 그걸 직접 부르지 않고 gh CLI를 즐겨 쓸까요? 이유가 셋 있어요.

  • 안정적 — API의 세세한 주소나 형식이 바뀌어도, gh 명령어의 사용법은 웬만해선 그대로예요. 로봇이 매번 고쳐 배울 필요가 없어요.
  • 인증이 간편 — gh auth login으로 한 번 로그인해 두면, 이후 명령마다 복잡한 토큰을 직접 다룰 필요가 없어요. 창구에 신분증을 한 번 맡겨두는 셈이에요.
  • 스크립트에 딱 — 한 줄짜리 명령이라, 자동화 스크립트 안에 그대로 끼워 넣기 좋아요. 결과도 프로그램이 읽기 좋은 형태로 받을 수 있어요.

정리하면, gh CLI는 사람이 만든 손잡이 달린 API예요. 로봇이 붙잡기 딱 좋은 손잡이라, 자동화의 첫 도구로 자주 선택돼요.

폴링 vs 이벤트 기반

이제 앞에서 미뤄둔 집배원과 초인종을 제대로 비교해요.

구분 폴링 (집배원) 이벤트 기반 (초인종)
방식 정해진 간격마다 직접 확인하러 감 변화가 생기면 GitHub이 알려줌
예시 5분마다 git pull·gh issue list로 새 변화 조회 웹훅(webhook), GitHub Actions의 트리거
장점 단순하고, 만들기 쉬움. 특별한 설정 없이 시작 가능 즉각 반응, 헛걸음 없음. 자원 낭비가 적음
단점 변화가 없어도 계속 확인 — 낭비·지연 발생 초기 설정이 필요하고 구조가 조금 복잡
어울리는 곳 가끔 확인해도 되는 일, 간단한 스크립트 즉시 반응해야 하는 일, 대규모 자동화

둘 중 무엇이 옳다기보다, 상황에 맞게 고르는 거예요. "하루 한 번 확인이면 충분한 일"에 초인종을 다는 건 과해요. 반대로 "새 PR이 열리면 1초 안에 반응해야 하는 일"에 5분 폴링은 너무 느려요. 이벤트 기반의 대표 주자가 바로 T18에서 배운 GitHub Actions예요 — "push되면 로봇을 깨워라"가 곧 초인종이죠.

"GitOps"라는 이름, 오해하지 마세요

자동화 이야기를 하다 보면 GitOps라는 말을 듣게 돼요. 그런데 이 이름이 오해를 많이 불러요. 두 가지를 분명히 나눠서 볼게요.

먼저 철학으로서의 GitOps. 이건 "git 저장소를 유일한 진실의 원천(single source of truth)으로 삼자"는 생각이에요. 즉, 무엇을 바꾸려면 저장소에 PR로 제안하고, 병합(merge)되는 순간 그것이 공식이 된다는 사고방식이에요. 눈치채셨나요? 이건 바로 앞 페이지 T25의 '결재 시스템' 그 자체예요. 새로운 도구가 아니라 일하는 태도예요.

그러니 이렇게 기억하세요. 철학(git을 진실로, merge를 승인으로)은 누구나, 어디서나 쓸 수 있는 태도예요. 도구(ArgoCD·Flux 같은 자동 동기화 장치)는 그 철학을 서버 운영에 적용한 특수 장비예요. 프로젝트는 도구 없이 철학만 빌려도 충분히 GitOps답게 일할 수 있어요.

오해 주의

GitOps는 특정 '도구'의 이름이 아니에요. 흔히 ArgoCD, Flux 같은 인프라 도구를 GitOps라 부르지만, 그건 더 좁고 특수한 이야기예요. 이 도구들은 저장소에 적힌 '원하는 상태'에 맞춰 실제 서버·클러스터를 자동으로 계속 일치시키는 동기화 장치예요. 반면 우리가 말한 철학(git=진실, merge=승인)은 그런 동기화 도구가 하나도 없어도 빌려 쓸 수 있어요. 문서 팀이 "규정은 저장소가 진실, 병합돼야 공식"이라고 정하는 것만으로 이미 GitOps 철학을 실천하는 거예요.

저장소 = 신뢰와 맥락의 경계

마지막으로 한 걸음 더 넓게 볼게요. 저장소(repository) 하나는 하나의 경계예요. 그 안에 무엇이 들어 있는지가 곧 '이 프로젝트가 아는 것의 전부'이고, 누가 접근할 수 있는지가 곧 '보안의 울타리'예요. 자동화 프로그램이나 AI 에이전트에게 저장소를 맡긴다는 건, 곧 "이 울타리 안의 것만 보고, 이 안에서만 일해라"라고 범위를 정해 주는 것과 같아요.

그래서 팀들이 종종 새 일에는 새 저장소를 파요. 서로 다른 프로젝트를 한 저장소에 뒤섞으면, 맥락이 엉키고(로봇이 엉뚱한 자료를 참고), 권한도 뭉뚱그려져(한 사람에게 열면 전부 열림) 위험해져요. 반대로 '한 프로젝트 = 한 저장소'로 나누면, 기억의 범위도 보안의 범위도 깔끔하게 하나로 맞아떨어져요.

이 관점은 사람에게도, 로봇에게도 똑같이 유효해요. 저장소를 '코드 창고'가 아니라 '하나의 맥락·신뢰 단위'로 보기 시작하면, 왜 팀들이 저장소를 그렇게 나누고 권한을 그렇게 거는지가 자연스럽게 이해돼요.

알아두면 좋은

지금까지 배운 조각들이 여기서 하나로 모여요. Projects(흐름), 조직·팀·권한(질서), PR/Merge(결재), 그리고 자동화(로봇). 이 넷을 '하나의 저장소'라는 경계 안에 담으면, 사람과 로봇이 함께 질서 있게 일하는 작은 운영 체계가 완성돼요. 여러분은 이제 그 지도를 손에 쥐었어요.
