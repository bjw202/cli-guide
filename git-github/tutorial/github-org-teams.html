조직과 팀, 권한이 흐르는 방식

여럿이 함께 쓰는 저장소는 '누가 무엇까지 할 수 있는가'를 정해야 해요. GitHub는 이걸 출입카드 등급처럼 다뤄요. 그리고 아주 중요한 역설 하나 — 권한이 있어도 못 하는 일이 있다는 사실을 함께 짚어볼게요.

이렇게도 써요

연구소·행정부서·운영팀처럼 사람이 많은 곳일수록 '누가 어디까지 손댈 수 있는가'가 중요해져요. GitHub의 조직·팀·권한은 이런 곳에서 '실수로 중요한 걸 건드리는 사고'를 막는 안전장치로 쓰여요.

회사 건물의 출입카드 등급

큰 회사 건물을 떠올려 보세요. 방문객 카드는 로비까지만, 일반 직원 카드는 사무실까지, 팀장 카드는 회의실과 자료실까지, 관리자 카드는 서버실까지 열 수 있어요. 같은 건물이지만 카드 등급에 따라 갈 수 있는 곳이 달라요.

GitHub의 권한(permission)도 똑같아요. 같은 저장소라도 누구는 읽기만, 누구는 코드까지 올리고, 누구는 설정까지 바꿀 수 있어요. 이 등급을 잘 나눠 두면, 실수도 줄고 사고도 막을 수 있어요.

비유

Organization은 '회사'고, Team은 그 안의 '부서'예요. 사람마다 카드를 일일이 발급하는 대신, "이 부서는 이 자료실까지"라고 부서 단위로 등급을 주면 관리가 훨씬 쉬워요. 새 직원이 와도 부서에 넣기만 하면 카드 등급이 자동으로 따라와요.

개인 계정과 조직은 달라요

개인 계정(personal account)은 말 그대로 '내 집'이에요. 저장소가 다 내 것이고, 내가 초대한 사람에게만 권한을 나눠줘요. 혼자 쓰거나 소수와 협업할 때 충분해요.

Organization(조직)은 '공동 건물'이에요. 저장소의 주인이 특정 개인이 아니라 조직 자체예요. 사람이 나가도 저장소는 조직에 남고, 팀 단위로 권한을 주고, 결제·보안 정책도 한곳에서 관리해요. 회사·오픈소스 커뮤니티·스터디 모임이 조직을 만드는 이유예요. T21에서 organization을 가볍게 스쳤다면, 여기서는 그 안의 '권한이 흐르는 방식'을 제대로 볼게요.

Team: 사람을 묶는 서랍

조직에 사람이 많아지면, 한 명 한 명에게 권한을 주는 건 금방 지쳐요. Team은 사람들을 부서처럼 묶는 서랍이에요. '연구팀', '행정팀', '운영팀'을 만들고, 팀 단위로 "이 저장소는 write까지, 저 저장소는 read만"이라고 정하면 끝이에요.

팀은 계층(부모 팀 아래 하위 팀)도 만들 수 있어서, 큰 조직의 부서 구조를 그대로 옮겨 담을 수 있어요. 사람이 팀에 들어오고 나가는 것만 관리하면, 권한은 팀을 따라 자동으로 흐르게 돼요.

5단계 출입카드: 권한 레벨

저장소 권한은 크게 다섯 등급이에요. 아래로 갈수록 할 수 있는 일이 많아지고, 위 등급은 아래 등급이 할 수 있는 일을 전부 포함해요.

권한 레벨 할 수 있는 일 (아래로 갈수록 누적) 누구에게
Read (읽기) 코드·Issue·PR 보기, 댓글 달기, clone·pull 구경하는 사람, 외부 참관자
Triage (분류) + Issue·PR 정리(라벨·담당자 지정, 닫기/열기). 코드는 못 올림 이슈를 정리하는 운영·커뮤니티 담당
Write (쓰기) + 브랜치에 push, PR 만들기, 코드 기여 실제로 작업하는 팀원
Maintain (관리) + 일부 저장소 설정 관리(민감 설정·삭제는 제외) 프로젝트 리드, 관리 보조
Admin (관리자) + 모든 설정, 권한 부여, branch protection 규칙 변경, 저장소 삭제 저장소 책임자

대부분의 팀원은 Write면 충분해요. 코드를 올리고 PR을 만드는 데 필요한 권한이 다 들어있거든요. Admin은 되도록 적게 — 건물 서버실 열쇠를 아무나 갖고 있으면 안 되는 것과 같아요.

핵심 역설: 권한이 있어도 못 할 수 있어요

여기가 이 페이지에서 가장 중요한 부분이에요. 방금 "Write 권한이 있으면 push할 수 있다"고 했죠. 그런데 Write 권한이 있어도 main 브랜치에 직접 반영하지 못하는 경우가 있어요. 왜일까요?

이유는 권한 레벨과 branch protection(브랜치 보호)이 서로 다른, 독립된 두 개의 관문이기 때문이에요. 둘은 겹겹이 쌓인 문이라, 앞문을 통과해도 뒷문이 잠겨 있으면 못 지나가요.

  • 권한 레벨은 "너는 이 저장소에서 무엇까지 할 수 있는가"를 정해요. (출입카드 등급)
  • branch protection은 "이 특정 브랜치(main)는 어떤 절차를 반드시 거쳐야 하는가"를 정해요. (특정 방의 잠금 규칙)

그래서 Write 카드를 가진 사람도, main이 보호되어 있으면 곧바로 push하지 못하고 반드시 PR을 거쳐 리뷰·승인을 받아야 해요. 카드 등급이 낮아서가 아니라, 그 방 자체에 '반드시 노크하고 허락받고 들어오라'는 규칙이 걸려 있는 거예요. branch protection은 T17 코드 리뷰에서 처음 만났던 그 규칙이에요.

주의

"권한을 줬는데 왜 main에 못 올리죠?"라는 질문은 대부분 이 역설 때문이에요. 권한 레벨을 올려도 소용없어요 — 막고 있는 건 권한이 아니라 branch protection 규칙이니까요. 이건 버그가 아니라 의도된 안전장치예요. 중요한 줄기일수록 "카드 등급과 상관없이 절차를 지켜라"가 맞는 방향이에요.

CODEOWNERS와 팀 권한이 만나면

T17에서 배운 CODEOWNERS를 기억하나요? '이 경로가 바뀌면 이 사람/팀이 리뷰한다'를 적어두는 파일이었죠. 이게 팀 권한과 만나면 아주 매끄럽게 돌아가요.

CODEOWNERS에 개인 대신 팀을 적어두면, 해당 경로를 건드리는 PR이 열릴 때 그 팀이 필수 리뷰어로 자동 지정돼요. 사람이 나가고 들어와도, 팀 명단만 관리하면 리뷰어가 늘 최신 상태로 유지돼요.

# .github/CODEOWNERS — 개인 대신 '팀'을 지정
# 문서 경로가 바뀌면 문서팀 전체가 자동 리뷰어
/docs/           @our-org/docs-team
# 데이터 파일은 연구팀이 리뷰
/data/           @our-org/research-team
# 설정 파일은 운영팀이 리뷰
/config/         @our-org/ops-team

여기서 세 겹이 함께 작동해요. 팀 권한이 '누가 무엇을 할 수 있나'를, CODEOWNERS가 '누가 어디를 검토하나'를, branch protection이 '그 검토를 반드시 거치게' 강제해요. 세 가지가 맞물리면, 큰 조직도 실수 없이 질서 있게 협업할 수 있어요.
