칸반보드로 일의 흐름 보기 — GitHub Projects

Issue가 '할 일 쪽지'라면, Projects는 그 쪽지들을 붙여 한눈에 흐름을 보는 '화이트보드'예요. 어떤 일이 지금 어디쯤 왔는지, 팀 전체가 같은 그림을 보게 해 주는 도구랍니다.

이렇게도 써요

연구팀이 '자료 수집 → 검토 → 정리 → 발표'라는 여러 단계 일을 화이트보드로 관리하듯, GitHub Projects도 코드가 아닌 '일의 진행 상황'을 보여주는 데 자주 쓰여요. 개발이 아니어도 '단계가 있는 일'이라면 어디든 어울려요.

팀 운영 사례 보기 →

회의실 화이트보드를 떠올려 보세요

회의실 벽에 큰 화이트보드가 있고, 거기에 '할 일 / 하는 중 / 검토 / 완료'라는 칸이 그어져 있다고 상상해 보세요. 각자 맡은 일을 포스트잇에 적어 붙이고, 일이 진행될 때마다 포스트잇을 오른쪽 칸으로 옮겨요. 지나가던 누구든 그 보드만 보면 "아, 이 일은 지금 검토 중이구나"를 알 수 있죠.

GitHub Projects는 바로 그 화이트보드의 디지털 버전이에요. 흩어져 있던 할 일들을 한 판 위에 모아, 지금 무엇이 어디쯤 와 있는지 팀 전체가 같은 그림으로 보게 해 줘요.

비유

Projects(v2)는 '조립식 화이트보드'예요. 칸의 이름도, 붙이는 쪽지에 적을 항목(마감일·우선순위·담당자)도 내 팀에 맞게 직접 정할 수 있어요. 정해진 양식이 아니라, 우리 일에 맞게 판을 짜 맞추는 느낌이에요.

Projects는 Issue를 대신하지 않아요

여기서 자주 헷갈리는 부분을 짚고 갈게요. T16에서 배운 Issue는 '할 일 하나하나를 적는 쪽지'예요. 반면 Project는 그 쪽지들을 끌어와 붙이는 판이에요. 둘은 경쟁 관계가 아니라 짝꿍이에요.

같은 Issue 하나가 판 위에서는 카드로 보이고, 판을 떠나도 Issue 그 자체는 그대로 남아요. Projects는 '새로운 할 일 저장소'가 아니라, 이미 있는 Issue와 PR을 모아 흐름과 상태로 보여주는 렌즈라고 생각하면 딱 맞아요.

칸의 정체: Status 필드

화이트보드의 '할 일 / 하는 중 / 검토 / 완료' 칸은 어디서 왔을까요? 이건 Status(상태)라는 단일 선택(single-select) 필드예요. 카드마다 상태를 하나 고르게 되어 있고, 같은 상태를 가진 카드끼리 한 칸(열)에 모여요.

기본값은 보통 Todo / In Progress / Review / Done 같은 값이지만, 이름도 개수도 우리 팀 방식대로 바꿀 수 있어요. 예를 들어 행정팀이라면 '접수 / 검토 / 결재대기 / 완료'로 고쳐 쓸 수 있죠. 카드를 다른 칸으로 끌어다 놓으면, 그 카드의 Status 값이 자동으로 바뀌어요.

github.com/dongne-library/library-web
Todo 0
대출 연장 기능 #38
지 지원
Status: Todo
In Progress 0
로그인 버튼이 안 눌려요 #42
민 민수
Status: In Progress
Review 0
로그인 버튼 클릭 영역 수정 PR #57
하 하늘 리뷰 중
Status: Review
Done 0

이건 보드 맛보기예요. 카드를 눌러 다음 칸으로 옮겨보세요. 뷰(보드·표·로드맵)와 필드, 자동화까지 보드를 운영하는 실전은 P06 보드 운영에서 만나요 →

쪽지에 무엇을 적을까: 필드 종류

Status 말고도, 카드에 원하는 정보를 붙일 수 있어요. 이게 커스텀 필드예요. 자주 쓰는 종류를 표로 정리했어요.

필드 종류 무엇을 담나 예시
text (텍스트) 자유롭게 쓰는 짧은 글 메모, 담당 부서 이름
number (숫자) 숫자 값 (합계·정렬 가능) 예상 소요 일수, 우선순위 점수
date (날짜) 특정 날짜 하나 마감일, 착수 예정일
single-select (단일 선택) 미리 정한 값 중 하나 Status, 우선순위(높음/중간/낮음)
iteration (반복 주기) 1~2주 단위의 작업 기간 이번 주 스프린트, 다음 주 스프린트

iteration이 조금 낯설 수 있어요. '2주씩 끊어서 일한다'는 주기를 미리 만들어 두고, 카드를 그 주기에 배정하는 거예요. "이건 이번 2주 안에, 저건 다음 2주에" 하고 시간의 서랍에 나눠 담는 셈이에요.

알아두면 좋은

필드는 '내 팀 언어'로 지을수록 좋아요. 개발팀이 아니어도 '검토자', '반려 사유', '결재 단계' 같은 필드를 만들어 쓰면, Projects가 곧 우리 팀 맞춤 업무 보드가 돼요. 정답 양식은 없어요. 우리 일에 맞으면 그게 정답이에요.

같은 자료, 다른 안경: 세 가지 뷰

Projects의 강점은 같은 데이터를 여러 방식으로 볼 수 있다는 거예요. 안경만 바꿔 끼면 같은 카드들이 전혀 다르게 보여요.

  • board 뷰(보드) — 우리가 계속 이야기한 화이트보드 모습. 칸(열)으로 나뉘어 있어 '흐름'을 보기 좋아요. 카드를 끌어 옮기며 상태를 바꿔요.
  • table 뷰(표) — 스프레드시트처럼 줄과 칸으로 보는 모습. 마감일·담당자·우선순위를 나란히 놓고 비교하거나 정렬할 때 편해요.
  • roadmap 뷰(로드맵) — 달력 위에 막대로 펼쳐 보는 모습. "이 일은 이번 달, 저 일은 다음 달"처럼 '시간 위의 계획'을 한눈에 봐요.

중요한 건, 세 뷰가 서로 다른 자료가 아니라는 점이에요. 카드는 하나인데, 보는 안경만 다른 거예요. 표에서 마감일을 고치면 로드맵에도 그대로 반영돼요.

한 쪽지가 여러 보드에 붙을 수 있어요

재미있는 사실 하나. 같은 Issue 하나가 여러 Project 보드에 동시에 올라갈 수 있어요. 예를 들어 '홈페이지 개편'이라는 일 하나가, 기획팀 보드에서는 '이번 분기 목표' 칸에, 운영팀 보드에서는 '검토 대기' 칸에 동시에 보일 수 있죠.

이건 포스트잇을 복사한 게 아니에요. 같은 쪽지를 두 화이트보드가 함께 바라보는 것에 가까워요. 그래서 한쪽에서 일이 끝나면, 그 사실을 다른 보드에서도 확인할 수 있어요. 팀마다 관심사는 다르지만 '일 자체'는 하나로 이어지는 셈이에요.

팁

처음부터 완벽한 보드를 만들려 애쓰지 마세요. 칸 3개(할 일 / 하는 중 / 완료)로 시작해, 팀이 익숙해지면 필드와 뷰를 하나씩 늘려가면 돼요. 화이트보드도 처음엔 선 몇 개로 시작하잖아요.
