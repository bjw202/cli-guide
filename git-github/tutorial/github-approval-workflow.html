PR과 Merge, 코드 너머의 결재

PR과 Merge는 사실 '코드 전용' 기능이 아니에요. '제안하고 → 검토받고 → 승인되면 공식이 되는' 결재 시스템이에요. 코딩을 한 줄도 몰라도, 어떤 팀이든 이 흐름을 그대로 빌려 쓸 수 있답니다.

이렇게도 써요

연구·행정·운영팀이 보고서·규정·데이터 파일을 GitHub에 올려두고, PR로 개정을 제안하고 결재하듯 승인해요. 코드가 아니라 '문서'를 다루는 팀도 이 결재 흐름 하나만으로 협업이 훨씬 깔끔해져요.

결재 문서함을 떠올려 보세요

회사에서 무언가를 바꾸려면 그냥 바꾸지 않죠. 기안서를 써서 올리고(상신), 관련자가 검토의견을 달고, 결재권자가 서명하면, 그제야 공식적으로 시행돼요. 반대로 문제가 있으면 반려되고, 이미 시행된 것도 나중에 철회할 수 있어요.

GitHub의 PR(Pull Request)과 Merge(병합)가 바로 이 결재 문서함과 똑같은 구조예요. T16에서 PR을 '변경을 제안하는 대화'로 배웠다면, 이번엔 한 걸음 물러서서 '결재 시스템'이라는 더 큰 그림으로 볼게요.

비유

Merge(병합)는 '결재 완료 도장'이에요. 도장이 찍히는 순간, 제안이던 변경이 공식 기록이 돼요. 그리고 그 도장을 누가 언제 찍었는지도 함께 남아요. 나중에 "이건 언제, 누구 승인으로 바뀐 거죠?"라는 질문에 문서함이 스스로 답해 주는 셈이에요.

결재 용어로 다시 읽는 PR

PR의 각 단계를 사무실 결재 용어로 나란히 놓으면, 낯설던 단어들이 갑자기 익숙해져요.

GitHub 용어 결재 문서함으로 치면 무슨 뜻
PR open (열기) 기안 상신 "이렇게 바꾸고 싶어요" 하고 제안서를 올림
review comment 검토의견 관련자가 "여긴 이렇게" 하고 의견을 달아줌
Approve (승인) 결재 서명 "좋습니다" 하고 승인 도장을 찍음
Merge (병합) 공식 승인·시행 변경이 공식 기록으로 반영됨 (되돌리기 어려운 확정)
Close (병합 없이 닫기) 반려 제안을 받아들이지 않고 접음
Revert (되돌리기) 승인 철회 이미 시행된 변경을 되돌림 — 이 철회 자체도 영구 기록으로 남음

특히 Revert가 흥미로워요. 결재를 철회한다고 원래 기안이 '없던 일'이 되진 않죠. "이런 결재가 있었고, 이런 이유로 철회했다"가 기록에 함께 남아요. GitHub의 revert도 똑같아요 — 지우는 게 아니라 되돌린다는 사실을 새 기록으로 추가해요. 그래서 나중에 흐름 전체를 되짚어 볼 수 있어요. (T11에서 만난 revert의 그 성격이에요.)

코드가 아니어도 돼요 — 핵심 메시지

이 페이지에서 꼭 가져갈 한 가지. PR/Merge는 코드 전용 기능이 아니에요. 그건 차이를 볼 수 있는(diffable) 모든 파일에 쓸 수 있는 범용 결재 도구예요.

  • 문서 — 규정, 매뉴얼, 보고서, 회의록의 개정을 PR로 제안하고 승인해요.
  • 설정 파일 — 서비스 설정값 변경을 눈으로 검토하고 승인 후 반영해요.
  • 데이터 — 표·목록·명단 같은 자료의 수정을 이력과 함께 남겨요.
  • 기획·정책 — "이렇게 바꾸자"는 제안을 글로 올리고, 관련자 승인을 받아 확정해요.

한 줄로 요약하면 이래요. '제안 → 검토 → 승인 → 공식화'가 필요한 팀이라면, 코드가 0줄이어도 이 흐름을 그대로 빌려 쓸 수 있어요. 텍스트로 된 파일이기만 하면, GitHub는 그걸 '결재 대상'으로 똑같이 대접해 줘요.

알아두면 좋은

많은 팀이 규정집·위키·정책 문서를 GitHub에 두는 이유가 이거예요. "누가, 언제, 왜, 누구 승인으로 이 규정을 바꿨는가"가 자동으로 남거든요. 종이 결재판이 하던 일을, 검색 가능하고 영원히 사라지지 않는 형태로 옮겨 놓은 셈이에요.

비개발자를 위한 diff 읽는 법

PR을 검토하려면 diff(차이)를 볼 줄 알아야 해요. 겁먹지 마세요. 코드가 아니라 문서의 diff는 생각보다 훨씬 쉬워요. 규칙은 딱 세 가지예요.

  • 빨간 줄 (앞에 -) — 지워진 내용이에요. "원래 이랬는데 뺐어요."
  • 초록 줄 (앞에 +) — 추가된 내용이에요. "이렇게 새로 넣었어요."
  • 색 없는 줄 (부호 없음) — 안 바뀐 내용이에요. 어디가 바뀌었는지 알아보라고 주변을 함께 보여주는 '맥락'일 뿐이에요.

아래는 어떤 안내 문서의 문장 하나를 고친 diff예요. 코드가 아니라 그냥 한국어 문장이죠?

  환영합니다. 이용 안내를 읽어 주세요.
- 문의는 평일 오전 9시부터 오후 5시까지 받습니다.
+ 문의는 평일 오전 9시부터 오후 6시까지 받습니다.
+ 주말·공휴일에는 답변이 하루 늦어질 수 있습니다.
  감사합니다.

읽어볼까요? 첫 줄과 마지막 줄은 안 바뀐 맥락이에요. 빨간 줄에서 '오후 5시'가 빠지고, 초록 줄에서 '오후 6시'로 바뀌었고, 안내 한 문장이 새로 추가됐네요. 이게 diff 읽기의 전부예요. 검토자는 이 세 색만 따라가며 "이 변경, 승인해도 될까?"를 판단하면 돼요.

1 PR = 1 승인 단위

결재를 올릴 때 서로 관련 없는 일 열 가지를 한 장에 몰아 담으면, 결재권자는 머리가 아파요. "이건 승인이고 저건 반려하고 싶은데, 한 장에 묶여 있으니 어쩌지?" 하게 되죠.

그래서 좋은 원칙이 '1 PR = 1 승인 단위'예요. 하나의 PR에는 하나의 목적만 담아요. '오타 수정'과 '정책 변경'은 각각 다른 PR로 나누는 거예요. 이렇게 하면:

  • 검토자가 한 번에 한 가지만 판단하면 되니 부담이 줄어요.
  • 일부만 문제가 있어도, 그 PR만 반려하고 나머지는 통과시킬 수 있어요.
  • 나중에 revert할 때도 '그 변경 하나만' 깔끔하게 되돌릴 수 있어요.

작게 나눌수록 결재가 빨라져요. 큰 제안서 하나보다, 명확한 제안서 여러 장이 훨씬 잘 굴러가요.

팁

이 페이지는 T16 Issue와 PR과 T17 코드 리뷰가 코드 중심으로 다룬 내용을, '코드 너머'로 넓힌 편이에요. 흐름이 헷갈리면 두 페이지를 다시 펼쳐 보세요. 같은 뼈대에 '결재'라는 옷을 입힌 것뿐이라는 게 보일 거예요.
