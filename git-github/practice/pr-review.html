Files changed에서 리뷰하기

PR #57의 '변경 파일' 탭이 리뷰의 진짜 무대예요. 바뀐 코드를 줄 단위로 보며 의견을 남기고, 여러 코멘트를 묶어 한 번에 제출해요. 아래 화면에서 직접 리뷰를 시작해보고, 비개발자에게 꼭 필요한 판단 기준까지 챙겨볼게요.

비유

코드 리뷰는 원고 교정과 똑같아요. 편집자는 원고 옆 여백에 "이 문장 어색해요", "여기 오타요" 같은 메모를 달죠. 그리고 메모를 한 줄씩 따로 보내는 게 아니라, 다 모아서 한 번에 "검토 끝났습니다"라며 돌려줘요. GitHub 리뷰도 이 방식이에요. 코드 옆에 코멘트를 달고, 모아서 한꺼번에 제출해요.

변경 파일과 diff 읽기

Files changed(변경 파일) 탭을 열면 diff(디프, 차이)가 나와요. 바뀌기 전 줄은 빨간 배경, 바뀐 후 줄은 초록 배경으로 보여줘요. 줄 앞의 빨강은 지워진 줄, 초록은 새로 넣은 줄이에요. PR #57은 파일 두 개를 고쳤어요. 아래 화면에서 직접 리뷰를 해볼 수 있어요. 코드 줄 위에 마우스를 올리면 왼쪽에 파란 + 버튼이 나타나요. 눌러서 그 줄에 코멘트를 달아보세요.

리뷰 도구 한 벌

diff 화면에는 리뷰를 돕는 작은 도구들이 있어요. 하나씩 볼게요.

  • 라인 코멘트 — 코드 줄 번호에 마우스를 올리면 나타나는 파란 +를 눌러, 그 줄에 딱 붙는 의견을 남겨요.
  • 멀티라인 코멘트 — 여러 줄에 걸친 의견이라면, +를 드래그하거나 시작 줄을 누른 뒤 끝 줄을 Shift+클릭해 범위로 코멘트를 달아요.
  • Suggested change(제안 변경) — 말로 "이렇게 바꾸면 어때요" 대신, 바뀐 코드 자체를 제안해요. 작성자는 Commit suggestion(제안 커밋)으로 클릭 한 번에 반영할 수 있고, 여러 제안을 모아 한 번에 커밋(batch)할 수도 있어요.
  • Viewed(확인함) — 파일별로 "이 파일은 다 봤어요" 체크박스예요. 단, 그 파일이 이후에 또 바뀌면 자동으로 해제돼서, 새로 바뀐 부분을 다시 보게 해줘요.
  • 기어(⚙) 아이콘 → Hide whitespace(공백 무시) — 띄어쓰기·들여쓰기만 바뀐 줄을 diff에서 숨겨, 진짜 바뀐 내용에 집중하게 해줘요.

보기 방식: Unified와 Split

실제 GitHub의 diff 화면에는 오른쪽 위 기어(⚙) 아이콘이 있어요. 거기서 diff를 보는 방식을 두 가지 중에 고를 수 있어요.

  • Unified(통합 보기) — 지운 줄과 넣은 줄을 위아래로 한 흐름에 이어 보여줘요. 화면이 좁을 때 편해요.
  • Split(분할 보기) — 왼쪽에 '바뀌기 전', 오른쪽에 '바뀐 후'를 나란히 놓아요. 무엇이 무엇으로 바뀌었는지 짝지어 보기 좋아요.
주의

위 재현 화면의 Unified/Split 버튼은 안내만 바뀌고 화면 모양은 그대로예요. 이 학습용 mock에는 Split(분할) 보기를 그리는 기능이 아직 없어서, 눌러도 좌우로 나뉘지 않아요(다시 그려지지 않아요). 진짜 GitHub에서는 앞서 말한 기어(⚙) 메뉴로 통합/분할을 오갈 수 있으니, 개념만 여기서 익혀두고 실제 전환은 GitHub에서 확인하세요.

배치 리뷰: 코멘트를 모아 한 번에

리뷰의 핵심은 모아서 제출이에요. 코멘트를 하나 달 때마다 알림이 가면 작성자가 피곤하니까, 다 적은 뒤 한 번에 보내요. 위 화면에서 +를 눌러 코멘트를 달면, 흐름이 이렇게 이어져요.

  • Start a review(리뷰 시작) — 첫 코멘트를 담으면 리뷰가 시작돼요. 이때 코멘트는 pending(대기) 상태예요.
  • pending은 지금 나에게만 보여요. 작성자는 아직 못 봐요. 마음 편히 여러 줄에 계속 달 수 있어요.
  • Add review comment(리뷰 코멘트 추가) — 두 번째부터는 이 버튼으로 계속 배치에 담아요.
  • Review changes(변경 사항 검토) → 마지막에 종류를 골라 Submit review(리뷰 제출)를 누르면, 담아둔 코멘트가 한꺼번에 공개돼요.

딱 한 줄만 짧게 남기고 싶다면, 배치를 거치지 않는 Add single comment(단건 코멘트)를 쓰면 즉시 하나만 제출돼요. "한 번에 모아 제출"이 배치 리뷰, "지금 하나만"이 단건이에요.

Comment · Approve · Request changes, 무엇을 고를까

Submit review 직전에 세 가지 종류 중 하나를 골라요. 원문 라벨 그대로예요.

  • Comment(코멘트) — 승인도 반대도 아닌 일반 의견이에요. "이건 어때요?", "궁금해요" 같은 말을 남길 때.
  • Approve(승인) — "이대로 합쳐도 좋아요"라는 확인 도장이에요. 저장소 규칙에 따라, 승인이 병합의 필수 조건이 되기도 해요.
  • Request changes(수정 요청) — "이건 고쳐야 합쳐요"라는 보류예요. 병합을 막는 신호가 될 수 있어요.
팁

비개발자를 위한 판단 기준. 여러분이 볼 수 있는 건 보통 "무엇을·왜 바꿨는가"이지, "이 코드가 기술적으로 안전한가"는 아니에요. 그러니 이렇게 하세요.

  • 기획 의도·화면 동작·문구가 맞는지 확인하고 싶다면 → Comment(코멘트)로 남겨요. "로그인 문구가 '로그인'이 맞아요" 같은 확인은 큰 도움이 돼요.
  • Approve(승인)는 코드의 기술적 타당성까지 책임진다는 뜻이라, 코드를 판단할 수 없다면 피하는 게 맞아요. 승인은 코드를 읽을 수 있는 리뷰어(예: 하늘·민수)에게 맡기세요.
  • 뭔가 이상해 보이지만 확신이 없다면 Request changes(수정 요청) 대신 Comment로 질문을 남기는 편이 부드러워요.
알아두면 좋은

Copilot code review(코파일럿 코드 리뷰, 2025년 4월 정식 출시)를 켜두면 AI가 자동으로 리뷰를 달아줘요. 다만 Copilot은 항상 Comment(코멘트)만 남겨요. 즉 자동 리뷰는 병합을 막지 않아요. 사람이 남기는 Approve/Request changes와 역할이 달라서, 참고 의견으로만 쌓여요.
