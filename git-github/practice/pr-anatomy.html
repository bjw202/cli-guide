실전 · P04 · GitHub 협업

PR 화면 해부: 4탭과 merge box

이슈가 '고쳐 달라는 요청'이라면, PR(Pull request)은 '이렇게 고쳤어요, 봐 주세요'라는 제출물이에요. 민수 님이 올린 PR #57을 열어, 위쪽 네 개의 탭과 아래쪽 병합 상자가 각각 무엇을 보여주는지 하나씩 짚어볼게요.

비유

PR은 학교에 내는 수행평가 제출함 같아요. 겉에는 '누가·무엇을 고쳤는지' 설명서(Conversation)가 붙고, 안에는 실제 답안(Commits·Files changed)이 들어 있어요. 선생님(검토자)이 확인 도장을 찍고, 통과 검사(Checks)가 모두 초록불이 되면, 비로소 제출함이 병합(merge)돼요. 오늘은 이 제출함을 겉부터 안까지 열어봐요.

PR 위쪽 네 개의 탭

PR #57 「로그인 버튼 클릭 영역 수정」을 열었어요. 민수 님이 fix/login-hitbox 브랜치에서 고친 것을 main 브랜치로 넣어달라고 올린 제출물이에요. 화면 위쪽에 탭이 네 개 있어요. 아래 화면에서 탭을 눌러보세요. 각 탭이 무엇을 보여주는지 바로 확인할 수 있어요.

github.com/dongne-library/library-web
로그인 버튼 클릭 영역 수정 #57
Open 민 민수 님이 fix/login-hitbox → main 병합을 요청했어요

Conversation(대화) — PR의 겉표지예요. 왜 고쳤는지 설명과 댓글, 리뷰 결과가 시간순으로 쌓여요.

민 민수 · 작성

로그인 버튼의 클릭 영역이 너무 작아 모바일에서 잘 안 눌렸어요. 버튼을 키우고 최소 높이를 넣었어요.

Closes #42

Commits(커밋) — 이 PR에 담긴 저장 지점 목록이에요. 어떤 순서로 고쳐왔는지 발자국이 보여요. 여기선 2개예요.

  • a1b2c3d 버튼 클릭 영역 확대
  • e4f5g6h 최소 높이 44px 추가

Checks(검사) — 자동으로 돌아간 통과 검사 결과예요. 빌드·테스트 같은 로봇 검사가 초록불인지 빨간불인지 보여줘요.

  • pass CI 빌드(빌드·테스트) 통과
  • pass Lint(코드 스타일 검사) 통과

Files changed(변경 파일) — 실제로 바뀐 코드를 줄 단위로 보여줘요. 리뷰는 주로 여기서 해요. 이 PR은 파일 2개를 고쳤어요. (다음 P05에서 이 탭을 깊게 다뤄요.)

  • src/components/LoginButton.jsx
  • src/styles/login.css
팁

비개발자는 보통 Conversation(대화) 탭에서 대부분의 일을 봐요. "왜 고쳤는지, 언제 통과됐는지, 누가 승인했는지"가 전부 여기에 모이거든요. Files changed(변경 파일)는 코드가 낯설면 훑어보기만 해도 괜찮아요. 대신 "무엇을·왜 바꿨는지"를 설명하는 Conversation의 글을 잘 읽는 게 더 중요해요.

아직 준비 중이에요: Draft → Ready for review

PR을 열었다고 바로 "봐 주세요"가 되는 건 아니에요. 아직 다듬는 중이라면 Draft(초안) 상태로 올릴 수 있어요. 제출함에 "작성 중" 팻말을 붙여둔 셈이에요.

  • Draft 상태에서는 자동 리뷰 요청이 가지 않아요. 검토자들에게 "아직 보지 마세요"라고 알려주는 거라, 괜히 미완성 코드로 알림을 보내지 않아요.
  • 다 준비되면 Ready for review(리뷰 준비 완료)를 눌러요. 이때 비로소 CODEOWNERS(코드 담당자) 규칙에 따라 정해진 검토자에게 알림이 가요.

그래서 순서를 이렇게 기억하면 좋아요. 초안으로 열기 → 다듬기 → Ready for review로 전환 → 그제야 리뷰어 호출.

닫기 키워드: Closes #42

PR #57 본문을 보면 Closes #42라는 한 줄이 있었죠. 이건 마법의 주문이에요. "이 PR이 병합되면 이슈 #42도 자동으로 닫아줘"라는 뜻이거든요. 우리 이야기에서 딱 그렇게 이어져요. PR #57이 병합되면 지원 님이 올린 #42 「로그인 버튼이 안 눌려요」가 저절로 닫혀요.

쓸 수 있는 닫기 키워드는 여러 개예요. Closes, Fixes, Resolves 뒤에 #이슈번호를 붙이면 돼요. 그런데 여기엔 꼭 알아야 할 조건이 하나 있어요.

주의

닫기 키워드(Closes #42 등)는 그 PR이 저장소의 default 브랜치(보통 main)를 대상으로 병합될 때만 이슈를 자동으로 닫아요. 만약 PR이 main이 아니라 다른 개발용 브랜치를 향하고 있다면, 병합돼도 이슈는 닫히지 않아요. 우리 PR #57은 fix/login-hitbox → main이라 조건을 만족해요. 그래서 병합 순간 #42가 닫혀요. "분명 Closes를 적었는데 이슈가 안 닫혔어요"의 대부분은 이 브랜치 조건 때문이에요.

병합 상자(merge box)

PR 화면 맨 아래에는 병합 상자(merge box)가 있어요. "지금 이 PR을 합쳐도 되나?"를 판단해주는 안내판이에요. 필요한 검사(required checks)가 모두 초록불이면 병합 버튼이 켜지고, 하나라도 빨간불이거나 대기 중이면 잠겨요. 아래에서 왼쪽의 동그란 토글을 눌러 검사를 통과/실패로 바꿔보세요. 상태 글자와 아래 병합 버튼이 함께 바뀌어요.

github.com/dongne-library/library-web
  • CI 빌드(빌드·테스트) — 통과
  • Lint(코드 스타일 검사) — 통과
  • 리뷰어 1명 승인(하늘) — 통과
병합할 수 있음

알아두면 좋은

병합 상자에는 상황에 따라 버튼이 더 나타나요.

  • Update branch(브랜치 업데이트) — 그새 main이 바뀌었다면, 그 최신 내용을 이 PR로 끌어와 맞춰줘요.
  • Enable auto-merge(자동 병합 켜기) — 지금 당장은 못 합치는 PR에만 보여요. 켜두면 검사가 다 통과되는 순간 자동으로 병합돼요. 밤새 검사가 끝나길 기다릴 필요가 없어요.
  • Merge when ready(준비되면 병합) — merge queue(병합 큐)를 쓰는 저장소에서, 순서를 지켜 안전하게 합치도록 대기열에 세워요.

병합 3종: 어떻게 합칠까

병합 버튼 옆 작은 삼각형(▾)을 누르면, 합치는 방식을 세 가지 중에서 고를 수 있어요. 원문 라벨 그대로 익혀두면 화면에서 바로 찾을 수 있어요.

  • Create a merge commit(병합 커밋 만들기) — PR의 커밋들을 그대로 두고 합침 지점 하나를 새로 찍어요. 발자국이 온전히 남아요.
  • Squash and merge(스쿼시 병합) — PR의 여러 커밋을 하나로 눌러 합쳐요. 기록이 깔끔해져서, 작은 PR에 많이 써요. (우리 #57 화면의 기본값이에요.)
  • Rebase and merge(리베이스 병합) — 커밋들을 합침 지점 없이 나란히 얹어요. 한 줄로 이어진 기록을 좋아하는 팀이 써요.

비개발자라면 "무엇을 고를까"보다 "우리 팀이 정한 기본값을 따른다"가 맞는 태도예요. 대부분의 팀은 셋 중 하나를 기본으로 정해두거든요.

이슈와 PR을 손으로 잇기: Development

Closes #42 같은 키워드를 안 적었더라도, 이슈와 PR을 수동으로 연결할 수 있어요. P02에서 봤던 이슈 사이드바의 Development(개발) 칸 기억나죠? 거기서 이 이슈를 고치는 PR이나 브랜치를 직접 골라 이어줄 수 있어요.

  • 이슈 #42 오른쪽 사이드바 → Development 칸의 톱니(⚙) → PR #57 선택.
  • 연결해두면 이슈에서 "이 문제를 지금 저 PR에서 고치는 중"이 보이고, 앞서 배운 linked:pr 검색에도 잡혀요.

정리하면, 이슈와 PR을 잇는 길은 둘이에요. PR 본문에 닫기 키워드를 적는 자동 방식과, 이슈의 Development 칸에서 고르는 수동 방식. 상황에 맞게 쓰면 돼요.
