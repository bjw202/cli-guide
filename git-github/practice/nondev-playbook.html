실전 · P08 · GitHub 협업

비개발자 플레이북

여기까지 왔으면 이제 GitHub 화면이 낯설지 않을 거예요. 마지막으로, 기획/PM·디자이너·QA가 각자 무엇을 하면 되는지, 코드 없이도 문서를 고쳐 올리는 방법, 손에 익으면 편한 gh 명령 몇 개, 그리고 절대 건드리면 안 되는 것을 한 장에 모았어요.

비유

공동 작업 GitHub은 여러 사람이 함께 쓰는 위키식 백과사전과 비슷해요. 아무나 본문을 바로 덮어쓰지 않고, "이 문단을 이렇게 고치자"는 제안을 따로 만들어 올리면, 편집자가 확인하고 반영하죠. 비개발자도 이 '제안' 방식만 지키면 코드 저장소에 얼마든지 기여할 수 있어요.

역할별 체크리스트

지원(기획/PM)·하늘(디자이너)·그리고 QA 담당이 GitHub에서 주로 하는 일을 역할별로 정리했어요. 대부분 Issues·Pull requests·Projects 안에서 이뤄져요.

기획 / PM (지원 님)

  • 새 요구사항·버그를 Issues에 이슈로 남겨요. 제목은 증상, 본문은 재현 순서·기대 동작으로.
  • 이슈에 Labels(라벨)·Milestone(마일스톤)·Assignees(담당자)를 붙여 분류·마감·담당을 정리해요.
  • Projects 보드에서 카드 상태를 훑고, 막힌 곳을 Comment(코멘트)로 물어요.
  • PR에는 기획 의도·화면 동작·문구가 맞는지 Comment로 확인해요. (코드 승인은 개발자에게.)

디자이너 (하늘 님)

  • 디자인 변경 요청·에셋 교체를 이슈로 남기고, 시안 이미지를 본문에 끌어다 붙여요.
  • PR의 Files changed(변경 파일)나 배포 미리보기에서 실제 화면을 보고, 여백·색·정렬이 시안과 맞는지 Comment로 짚어요.
  • 문구·스타일 문서(예: README·가이드 문서)는 웹 에디터로 직접 고쳐 PR을 올려도 돼요(아래 방법).

QA

  • 버그를 재현 순서·기대 결과·실제 결과 형태로 이슈에 적어요. 스크린샷·영상은 본문에 붙여요.
  • 고쳤다는 PR이 올라오면, 배포 미리보기에서 다시 테스트하고 결과를 Comment로 남겨요.
  • 여전히 문제가 있으면 이슈를 닫지 말고, 무엇이 남았는지 코멘트로 알려요.

코드 없이 문서 고쳐 PR 올리기

터미널도, Git 명령도 필요 없어요. GitHub 웹 화면만으로 문서를 고쳐 Propose changes(변경 제안)까지 올릴 수 있어요. 오타 하나를 고친다고 해볼게요.

  • 고칠 파일(예: README.md)을 GitHub에서 열고, 오른쪽 위 연필 아이콘(✏)을 눌러요. 편집 모드가 열려요.
  • 내용을 고친 뒤, 오른쪽 위 Commit changes(변경 사항 커밋)를 눌러요.
  • 뜨는 창에서 Create a new branch for this commit and start a pull request, 곧 Create a new branch(새 브랜치 만들기)를 골라요. main에 바로 쓰지 않고 내 제안용 가지에 담는 거예요.
  • Propose changes(변경 제안)를 누르면 PR 작성 화면으로 이어져요. 제목·설명을 적고 PR을 만들면 끝이에요.

이 흐름은 앞서 P04·P05에서 본 PR·리뷰로 그대로 이어져요. 내가 만든 제안을 리뷰어가 보고, 좋으면 병합하는 거예요.

팁

웹 에디터로 만든 브랜치 이름은 GitHub이 알아서 제안해줘요(예: 지원-patch-1). 그대로 두어도 되고, 알아보기 쉬운 이름으로 바꿔도 돼요. 중요한 건 main이 아닌 별도 가지에 담긴다는 점이에요.

gh CLI 맛보기

같은 일을 터미널에서 gh(GitHub 공식 CLI) 명령으로도 할 수 있어요. 지금 당장 외울 필요는 없지만, 팀에서 이런 줄을 보면 무슨 뜻인지 알아볼 수 있게 눈에 익혀두세요.

# 이슈 만들기 (제목·본문을 대화형으로 입력)
gh issue create

# 초안(Draft) 상태로 PR 만들기 — 아직 리뷰 요청 전
gh pr create --draft

# PR 리뷰 남기기 — 승인 / 수정 요청 / 일반 의견 중 하나
gh pr review --approve
gh pr review --request-changes
gh pr review --comment

# 스쿼시로 병합하되, 조건이 갖춰지면 자동 병합(auto)
gh pr merge --squash --auto

# 프로젝트 보드에 항목 추가
gh project item-add

각 명령이 화면의 어떤 버튼과 짝인지 보이나요? gh pr review --approve는 Approve(승인) 버튼, --squash는 Squash and merge(스쿼시 병합)와 같은 동작이에요. CLI는 그 버튼들을 글자로 부르는 것뿐이에요.

알아두면 좋은

gh CLI와 자동화의 큰 그림이 궁금하면 T26 gh CLI·자동화·GitOps를 보세요. 여기서는 "이런 게 있다" 정도만 맛보고, 실제로는 위의 웹 에디터 방식만으로도 대부분의 비개발자 기여가 가능해요.

주의

이건 절대 하지 마세요.

  • force push(강제 푸시) — 남의 기록을 덮어써 되돌릴 수 없게 만들 수 있어요. 공용 브랜치에서는 특히 금물이에요. 명령에 --force가 보이면 멈추고 개발자에게 물어보세요.
  • main에 직접 커밋 — 검토 없이 공식 브랜치를 바로 고치는 일이에요. 위에서 배운 대로 항상 새 브랜치 → PR로 제안하세요. 웹 에디터가 Create a new branch(새 브랜치 만들기)를 권하는 이유가 바로 이거예요.
