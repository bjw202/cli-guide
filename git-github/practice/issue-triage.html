실전 · P03 · GitHub 협업

잘 쓴 이슈, 나쁜 이슈

같은 문제라도, 이슈를 어떻게 적느냐에 따라 해결까지 걸리는 시간이 크게 달라져요. #42를 좋은 예로 삼아, 잘 쓴 이슈의 조건과 그걸 자동으로 갖추게 해주는 템플릿, 그리고 쌓인 이슈를 빠르게 찾고 정리하는 법까지 익혀볼게요.

비유

이슈를 쓰는 건 병원에서 진료 접수증을 쓰는 것과 같아요. "그냥 아파요"라고만 적으면 의사가 이것저것 되물어야 해요. 하지만 "어제 저녁부터, 오른쪽 배가, 걸을 때 특히 아파요"라고 적으면 곧장 진찰로 넘어가죠. 이슈도 똑같아요. 무엇이·언제·어떻게가 담긴 접수증이 해결을 앞당겨요.

잘 쓴 이슈 vs 나쁜 이슈

먼저 나쁜 예부터 볼게요. 아래처럼 적으면 담당자는 아무것도 시작할 수 없어요.

  • 제목: "안 돼요" — 뭐가 안 되는지 알 수 없어요.
  • 본문: "로그인이 이상함" — 어느 화면에서, 어떻게 눌렀을 때, 무엇을 기대했는지가 없어요.
  • 꼬리표: 라벨도, 유형도, 담당자도 없음 — 급한지 아닌지, 누가 볼지 알 수 없어요.

이제 우리 #42 「로그인 버튼이 안 눌려요」를 볼까요. 같은 문제인데 접수증이 완전히 달라요. 아래는 그 이슈를 다시 그린 화면이에요.

github.com/dongne-library/library-web
로그인 버튼이 안 눌려요 #42
Open 지 지원 님이 열었어요 · 코멘트 3개 bug priority:high
지 지원 · 작성

무슨 일이 일어나나요. 로그인 페이지에서 파란 로그인 버튼을 눌러도 아무 반응이 없어요.

재현 방법. 1) 로그인 페이지 열기 → 2) 파란 로그인 버튼 클릭 → 3) 아무 일도 안 일어남.

기대한 결과. 로그인 창이 뜨거나, 로그인이 진행돼야 해요.

환경. 모바일(아이폰 사파리)에서 특히 자주, 데스크톱에서도 가끔.

팁

좋은 이슈에는 보통 네 가지가 들어가요. ① 무슨 일이 일어나나요(현상), ② 재현 방법(순서대로), ③ 기대한 결과, ④ 환경(기기·브라우저). 이 네 칸만 채우면, 코드를 몰라도 개발자가 곧장 원인을 찾기 시작할 수 있어요. #42가 딱 그렇게 쓰여 있죠.

이슈 템플릿 ①: Issue Forms (양식형)

매번 "네 칸을 채워주세요"라고 부탁하긴 번거로워요. 그래서 GitHub은 이슈 템플릿(issue template)을 제공해요. 새 이슈를 열 때 미리 만든 빈 양식이 뜨는 거예요. 가장 강력한 방식이 Issue Forms(양식형 이슈)예요. 저장소의 .github/ISSUE_TEMPLATE/ 폴더에 *.yml 파일로 넣어두면, 진짜 설문지처럼 칸이 생겨요.

쓸 수 있는 칸(입력 요소)은 네 종류예요.

  • input(한 줄 입력) — 짧은 답. 예: "발견한 페이지 주소".
  • textarea(여러 줄 입력) — 긴 설명. 예: "재현 방법".
  • dropdown(드롭다운 선택) — 정해진 보기 중 고르기. 예: "브라우저".
  • checkboxes(체크박스) — 여러 개를 켤 수 있는 확인 목록.

각 칸에는 validations(유효성 검사)로 required: true(필수)를 걸 수 있어요. 그러면 그 칸을 비운 채로는 이슈를 제출하지 못하게 막아줘요.

# .github/ISSUE_TEMPLATE/bug_report.yml  (Issue Forms 양식형)
name: 버그 신고
description: 안 되는 것을 접수해요
labels: ["bug"]
body:
  - type: input
    id: page-url
    attributes:
      label: 어느 화면인가요
      placeholder: 예) 로그인 페이지
    validations:
      required: true

  - type: textarea
    id: steps
    attributes:
      label: 재현 방법
      description: 순서대로 적어주세요 (1 → 2 → 3)
    validations:
      required: true

  - type: dropdown
    id: browser
    attributes:
      label: 어떤 브라우저인가요
      options:
        - 크롬(Chrome)
        - 사파리(Safari)
        - 엣지(Edge)

  - type: checkboxes
    id: checks
    attributes:
      label: 확인했어요
      options:
        - label: 새로고침해도 같은 문제가 나요
        - label: 다른 기기에서도 재현돼요

이슈 템플릿 ②: Markdown 템플릿과 config.yml

Issue Forms 말고, 더 간단한 Markdown 템플릿도 있어요. .github/ISSUE_TEMPLATE/ 안에 *.md 파일로 두면, 그 파일의 내용이 새 이슈 본문에 미리 채워진 초안으로 들어가요. 맨 위에는 --- 로 감싼 frontmatter(머리말)를 적어, 목록에 어떻게 보일지 정해요.

  • name: — 템플릿을 고르는 화면에 뜨는 이름.
  • about: — 그 이름 밑에 붙는 한 줄 설명.

둘의 차이는 이래요. Issue Forms(.yml)는 칸을 나눠 필수 입력을 강제할 수 있어 비개발자에게 특히 친절해요. Markdown(.md)은 그냥 빈칸 초안이라 자유롭지만, 사용자가 지워버릴 수도 있어요. 처음이라면 Issue Forms를 권해요.

마지막으로 같은 폴더의 config.yml은 '템플릿 고르는 화면' 전체를 다뤄요.

  • blank_issues_enabled — false로 두면 빈 이슈로 바로 열기를 막아, 반드시 템플릿을 거치게 해요.
  • contact_links — 이슈 대신 안내할 다른 창구(예: 고객 문의 폼, 커뮤니티)를 링크로 걸어둬요.
# .github/ISSUE_TEMPLATE/bug_report.md  (Markdown 템플릿)
---
name: 버그 신고(간단)
about: 짧게 접수하고 싶을 때
labels: bug
---

## 무슨 일이 일어나나요

## 재현 방법
1.
2.

## 기대한 결과


# .github/ISSUE_TEMPLATE/config.yml  (템플릿 고르는 화면 설정)
blank_issues_enabled: false
contact_links:
  - name: 이용 문의(도서관 데스크)
    url: https://example.com/help
    about: 코드 문제가 아니라면 여기로 문의해 주세요
알아두면 좋은

템플릿은 강제가 아니라 안내예요. 잘 만든 양식 하나가, "이슈 좀 자세히 써 주세요"라는 잔소리를 열 번 하는 것보다 효과가 커요. 기획/PM인 지원 님이 개발자에게 부탁해 양식을 한 번 만들어두면, 이후로는 접수받는 모든 이슈가 저절로 반듯해져요.

쌓인 이슈에서 원하는 것만 찾기: 검색 qualifier

이슈가 수십 개로 늘면, 눈으로 훑기 어려워요. GitHub 이슈 검색창에는 qualifier(한정어)라는 특별한 단어들을 넣을 수 있어요. 이름:값 꼴로 적으면, 그 조건에 맞는 이슈만 걸러줘요. 아래는 실제로 쓰이는 표현 그대로예요. 검색창에 이어 붙이면 조건이 AND(모두 만족)로 좁혀져요.

# 이슈 검색창에 그대로 넣어보세요 (여러 개를 이어 붙이면 조건이 좁아져요)
is:open                열려 있는 것만
label:"in progress"    라벨 이름에 공백이 있으면 큰따옴표로 감싸요
-label:bug             앞에 빼기(-)를 붙이면 "그 라벨이 없는 것"
assignee:              담당자로 거르기 (assignee:민수 처럼 뒤에 사람)
milestone:             마일스톤으로 거르기 (milestone:"v1.0 오픈")
type:bug               이슈 유형이 Bug 인 것
no:label               라벨이 하나도 없는 것 (분류가 빠진 이슈 찾기)
no:assignee            담당자가 없는 것 (주인 없는 이슈 찾기)
no:milestone           마일스톤이 없는 것
no:project             어떤 프로젝트에도 안 올라간 것
linked:pr              연결된 PR이 있는 것 (지금 누가 고치는 중)
팁

no:로 시작하는 것들이 정리에 특히 유용해요. no:label로 분류가 빠진 이슈를, no:assignee로 주인 없는 이슈를 한 번에 모아, 라벨과 담당자를 채워 넣으면 게시판이 금방 깔끔해져요. 반대로 linked:pr은 "지금 실제로 손대는 중인 문제"만 골라 보고할 때 좋아요.

한꺼번에 정리하기: 일괄 편집·Pin·Transfer·Convert

검색으로 골라낸 이슈들을, 손으로 하나씩 고치지 않아도 돼요. 이슈 목록 화면에는 여러 개를 한 번에 다루는 도구가 있어요.

  • 일괄 편집(bulk edit) — 목록에서 이슈 여러 개를 체크한 뒤, 위쪽 버튼으로 라벨·담당자·마일스톤·상태를 한 번에 바꿔요. "주인 없는 버그 다섯 개에 담당자 붙이기"가 클릭 몇 번이면 끝나요.
  • Pin issue(이슈 고정) — 중요한 이슈를 목록 맨 위에 압정으로 꽂아둬요. 저장소마다 최대 3개까지 고정할 수 있어요.
  • Transfer issue(이슈 이전) — 이슈를 다른 저장소로 옮겨요. 단, 같은 소유자(계정·조직)의 저장소끼리만 옮길 수 있어요. "이건 우리 팀 저장소가 아니라 디자인 저장소 일이네" 할 때 써요.
  • Convert to discussion(토론으로 전환) — 버그가 아니라 "이거 어떻게 할까요?" 같은 열린 대화라면, 이슈를 Discussions(토론)으로 바꿔요. 답을 정해야 하는 할 일이 아니라, 의견을 모으는 자리로 옮기는 거예요.
이렇게도 써요

지원 님의 월요일 아침 루틴: ① is:open no:label로 분류 안 된 새 이슈를 모아 라벨을 붙이고, ② is:open no:assignee label:bug로 주인 없는 버그를 골라 일괄 편집으로 담당자를 지정하고, ③ 이번 주 꼭 봐야 할 이슈 하나를 Pin issue로 꽂아둬요. 코드 한 줄 없이, 게시판 관리자로서 팀의 하루를 정돈하는 거예요.
